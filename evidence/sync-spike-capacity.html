정각 동기화 스파이크: 처리 용량 측정과 병목 분해

한 주기(30분)에 76만~144만 명의 동기화를 처리할 수 있습니다.

이벤트 한 건의 처리 시간은 커밋 때 WAL을 디스크에 동기화하는 횟수에 비례했고, 행 잠금 대기는 0%였습니다.

질문

정각에 한꺼번에 들어온 N건을 다음 정각(1,800초) 전에 다 처리하는지 확인했습니다.

Health는 30분마다 동기화하고, 다 처리하지 못하면 다음 정각분이 밀린 양 위에 또 쌓이기 때문입니다.

비동기 구조라 처리량은 API 응답 시간이 아니라, 컨슈머가 쌓인 이벤트를 소진하는 속도로 정의했습니다.

측정 방법

이벤트는 HTTP가 아니라 Kafka 토픽에 직접 넣었습니다.

동기화 API를 거치면 앞단 Health의 AI 호출(4~16초)이 먼저 병목이 되어 Game의 컨슈머를 잴 수 없기 때문입니다.

컨슈머를 얼린 채 N건을 다 쌓은 뒤 풀어서, 다 처리할 때까지의 시간만 쟀습니다.

발행 속도와 처리 속도가 완전히 분리되고, "정각에 N건이 이미 쌓여 있다"는 최악의 순간이 그대로 재현되기 때문입니다.

주입 (run_spike.sh)

docker pause "$GAME"                         # 컨슈머를 얼린다
jmeter "$MEAS" "$N" "$T" "${T:0:10}" main 1.5  # N건 발행
drain_start_ms=$(date +%s%3N)
docker unpause "$GAME"                       # 여기서부터 소진 시간

소진 시간 (03_result.sql)

SELECT count(*)                                              AS processed,
       (max(done_ms) - :drain_start_ms) / 1000.0              AS drain_sec,
       count(*) / ((max(done_ms) - :drain_start_ms) / 1000.0) AS per_sec
  FROM r;   -- r = 이번 회차 측정 유저의 스냅샷 저장 시각(updated_at)

측정 방법이 두 번 바뀐 이유

처음 두 회차는 컨슈머가 아니라 다른 것을 재고 있었습니다.

회차발행소진판단
S0 · 1,000건 · JMeter 반복 1,000회5.20초5.39초소진이 발행을 0.19초 차로 따라감 → 부하 도구(0.5코어)가 병목
S0 · 5,000건 · 샘플 1개 안에서 반복9.21초14.86초쌓이긴 했지만 발행 중 처리와 발행 후 처리가 섞여 처리량을 못 읽음
이후 전부 · 컨슈머 정지 후 적재0.6~1.0초아래 표발행 속도와 소진 속도가 완전히 분리됨

시나리오: 경로의 양 끝

실제 사용자 비율은 근거가 없어 임의로 정하지 않고, 가장 가벼운 경우와 가장 무거운 경우를 쟀습니다.

어떤 비율이든 이 두 값 사이에 든다고 말할 수 있기 때문입니다.

시나리오시드이벤트 한 건이 타는 경로
S0 가벼운 끝유저만, 퀘스트 없음스냅샷 조회 · 저장 → 퀘스트 없음 → 파티 퀘스트 없음
S2 무거운 끝전원 개인 퀘스트 + 4인 파티 퀘스트 진행 중위 경로 + 퀘스트 판정 · 갱신 + 멤버 행 · 공유 카운터 갱신 + 완료 선점 시도

30분이면 S0 기준 약 144만 명, S2 기준 약 76만 명을 처리합니다.

초당 800건 × 1,800초, 초당 423건 × 1,800초이기 때문입니다.

앞선 실험 로그에서 보였던 건당 0.6초는 실제 값이 아니었습니다.

워밍업 500건을 먼저 넣은 뒤 잰 스레드당 건당 시간은 3.7~7.1ms였기 때문입니다.

S2에서도 정합성은 맞았습니다. 개인 판정 20,000 · 파티 멤버 판정 20,000 · 공유 카운터 5,000개가 움직였고, 카운터와 멤버 기여분 합계가 어긋난 파티는 0개였습니다.

병목 분해 (S2 · 20,000건)

두 시나리오 모두 CPU가 남았습니다(2코어 중 약 1.2코어 사용).

그래서 스레드가 계산이 아니라 무언가를 기다리고 있다고 보고, 무엇을 기다리는지 세 방향에서 쟀습니다.

해석

병목은 커밋할 때 PostgreSQL이 WAL을 디스크(EBS)에 동기화하는 시간이었습니다.

S0은 파티 트랜잭션이 조회만 하고 끝나 WAL을 쓰지 않아 디스크 동기화 커밋이 건당 1회이고, S2는 두 트랜잭션 모두 UPDATE가 있어 2회입니다.

건당 시간이 이 횟수에 거의 비례했고(3.7ms → 7.1ms), CPU가 남는 것과도 맞습니다.

파티 공유 행 경합은 병목이 아니었습니다. 행 잠금 대기가 0%였기 때문입니다.

환경

  • 주입: JMeter 5.6.3(kafka-clients)를 같은 Docker 네트워크의 컨테이너로 실행, 메모리 768MB · 워밍업 0.5코어 · 본 주입 1.5코어(컨슈머가 얼어 있는 동안)
  • 워밍업: 다른 유저 500건을 먼저 처리해 JIT · 커넥션 풀 콜드 스타트 제거
